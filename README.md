# P501 FFT example - a streaming FFT on the AD9361 data, as a PYNQ overlay

A starting point for doing signal processing in the FPGA on the PZSDR P501 (Zynq UltraScale+ XCZU5EV + AD9361).
> **Layout:** clone this repository next to the [puzi501iio](https://github.com/fllay/puzi501iio) repository (folder `pzsdr-p501`), so that `../pzsdr-p501/hdl/library` exists: it provides the packaged ADI IP the design uses. Otherwise pass `LIB=<path to its hdl/library>` or set `P501_HDL_LIBRARY`.

**Method: [the design flow](tutorial/DESIGN_FLOW.md)** (float model, integer model, RTL, overlay, board, GNU Radio) behind every chapter. **New here? Two tutorials start from the base design and add blocks one by one: [FFT on the ADC data](tutorial/TUTORIAL.md) and [a hardware DDS on the DAC](tutorial/TUTORIAL_DDS.md). A third puts them together: [tone in, spectrum out, over the air, all in hardware](tutorial/TUTORIAL_DDS_FFT.md).**

## What is in this repository: the overlays at a glance

Every design here is a **separate PYNQ overlay** (its own `.bit` and `.hwh`, its own folder on the board). They are all generated by the same `create_project.tcl`: it builds the shared P501 base design (Zynq PS, `axi_ad9361`, the ADI RX/TX DMAs, Ethernet) and then adds one chain chosen by an option. To try another idea you build and load another overlay; the chains of the QPSK receiver variants are alternatives (they all sit at the same AXI address, so the script refuses to combine them).

The four QPSK receiver chains (FLL, 4th-power estimator, chain 3, frame sync) are four different answers to the same question, *how does the receiver find the carrier and the frame start?*; the 16-QAM overlay takes the answers that worked (FLL in front because the radios' natural offset of about 9.7 kHz is larger than the sync word tolerates, a known word for the frame start); the OFDM overlay needs neither a timing loop nor a phase loop (one tap per subcarrier and four pilots instead) and finds the frame with a Schmidl-and-Cox symbol. Each one has a live notebook in `notebook/` and a bit-exact fixed-point model in Python that the RTL is verified against in simulation before any bitstream is built (model first, then RTL, then board). All of them close timing at 100 MHz.

### Roadmap: a lab course in digital modulation on the P501

Each stage is an overlay plus a notebook, a bit-exact Python model, and a reference radio (B210 + GNU Radio) where one exists. Order of the stages:

| # | Stage | State |
|---|---|---|
| 1 | FFT and DDS in the FPGA | done |
| 2 | QPSK with the synchronisation variants (Costas, FLL, 4th-power estimator, m-sequence frame sync) | done |
| 3 | 16-QAM with a Zadoff-Chu frame synchroniser (advanced: 7.3 dB more SNR than QPSK, see the link report) | done |
| 4 | OFDM, 16-QAM data with QPSK training and pilots: IFFT and cyclic prefix, detection by delay-and-correlate, carrier offset (the natural 9.7 kHz is 0.16 of the 60 kHz spacing), channel estimate from known QPSK training symbols, per-symbol pilot correction; N = 64 at 3.84 MS/s, 28 used subcarriers, 4.2 Mb/s. Overlay `p501_ofdm_rx_sc` (`FFT=0 OFDMRXSC=1`: Schmidl-Cox detector, the host sends the frame through the DAC DMA) | designed, bit-exact integer model and RTL, built and tested on the board: digital loopback 0 errors in 2 M symbols, B210 to P501 at 850 MHz no symbol error in 51 M symbols at 82 dB gain (SNR 27.5 dB); live notebook, a block-by-block GNU Radio receiver and a receiver and transmitter from the stock GNU Radio OFDM blocks, and the 128-sample STS variant as the second overlay `p501_ofdm_rx_sts` (`OFDMRXSTS=1`): [tutorial 6](tutorial/TUTORIAL_OFDM.md), [plan](tutorial/ofdm/PLAN_OFDM.md), [report](tutorial/ofdm/REPORT_OFDM.md); next an FPGA transmitter |
| 5 | Chirp spread spectrum (LoRa-style): dechirp and FFT peak, the FFT block of stage 1 reused; low rate, very robust; separating timing from carrier offset with up- and down-chirps | planned (after OFDM) |
| 6 | Forward error correction, common to all of them (convolutional code with Viterbi; polar code with CRC-aided list decoding as the advanced version) | simulated (`tutorial/qam16/LINK_REPORT_QAM16.md` section 10) |
| 7 | An application: chat (chirp spread spectrum or QPSK, low rate, software decoder) or picture / video (16-QAM or OFDM with FEC, about 1.9 Mb/s at rate 1/2) | planned |

FEC comes last on purpose: students first see how each modulation fails on its own (EVM, constellation, error rate against level), and the code is then the fix; the same code serves every modulation because it only needs soft values.

**Three things to settle before the new stages are built**

1. **A common soft-output interface.** Every receiver should export one stream: a signed 8-bit soft value per coded bit plus a frame-start flag (soft symbols for QPSK and 16-QAM, FFT peak magnitudes for chirp spread spectrum, per-subcarrier values for OFDM). Today only the 1024-symbol capture RAM exists, which is too little for streaming FEC.
2. **A data-interface stage before the application.** The transmitters send a fixed PRBS payload. An application needs real data in and out: a packet format (header, length, CRC, sequence number) and a path from the processor (registers for a chat, DMA for video). The convolutional decoder is about real time in software (1 ms per frame on a PC); the polar list decoder (about 20 ms per frame) would need the FPGA for video.
3. **The application chooses the modulation:** chat on chirp spread spectrum or QPSK, picture or video on 16-QAM or OFDM with FEC.

**Wired lab setup.** The B210 over the air is not reproducible: its transmitter state changes between restarts and sessions (EVM -17 to -23 dB at the same level, `tutorial/qam16/LINK_REPORT_QAM16.md` sections 5c and 5d). The labs should therefore run on, in this order, (a) the AD9361's internal digital loopback (EVM -30 dB, works every time), (b) a cable from the P501's TX to its RX through a fixed attenuator, (c) the B210 and antennas as an optional step. Every step shows the received level and the EVM so that a student can tell a good link from a bad one; the uncoded labs measure constellations, EVM and error rate against level, not error-free transfer.

One Tcl script creates a Vivado 2024.1 project that contains

* the **P501 base design** (Zynq PS, `axi_ad9361`, the ADI RX/TX DMAs, the RGMII Ethernet bridge) - recreated
  from the libiio/IIO reference project, which stays untouched (`../pzsdr-p501`), and
* a small **FFT chain** hanging off the AD9361 ADC data: frame generator -> Xilinx FFT -> |X|^2 -> FIFO -> DMA -> DDR.

The result is a PYNQ overlay (`.bit` + `.hwh`) from which Python reads FFT frames computed in the FPGA.

```
axi_ad9361 (clock l_clk = 2 x sample rate in 1R1T)
  adc_data_i0 / adc_data_q0 / adc_valid_i0
        |-----------------------> util_ad9361_adc_fifo -> cpack -> axi_ad9361_adc_dma   (unchanged raw capture)
        v
  fft_framer  (rtl/adc_frame_gen.v)    {Q,I} -> AXI-Stream, TLAST every N samples
        v
  fft_core    Xilinx FFT 9.1           pipelined streaming, 16 bit, scaled, natural order
        v                              (config word held constant: forward, fixed scaling)
  fft_power   (rtl/fft_power_gate.v)   |X|^2 (32 bit) + frame gate: a frame passes only while the DMA is running (the FIFO behind it is flushed between transfers)
        v
  fft_fifo    AXI-S FIFO, 2 frames
        v
  fft_dma     ADI axi_dmac, AXI-Stream source  ->  DDR through HPC0        control registers at 0x9C440000
```

Everything on the FFT side runs on `l_clk`; the DMA crosses into the PS clock internally.

## Quick start

Requirements: Vivado 2024.1, and the packaged ADI hdl library (the `library/` folder of the
[puzi501iio / pzsdr-p501](https://github.com/fllay/puzi501iio) repository). The script looks for it at
`../pzsdr-p501/hdl/library`; otherwise pass `LIB=` or set `P501_HDL_LIBRARY`.

```bash
# create the project, then look at it in the GUI
vivado -mode batch -source create_project.tcl
vivado build/p501_fft/p501_fft.xpr          # open the block design "system": FFT chain is the fft_* cells

# or build everything through the bitstream and collect the overlay files
vivado -mode batch -source create_project.tcl -tclargs RUN=bit
python3 tools/fix_hwh.py build/overlay/p501_fft.hwh        # make the HWH loadable by PYNQ (see below)
```

`create_project.tcl` options (`key=value` after `-tclargs`):

| option | default | meaning |
|---|---|---|
| `NFFT_LOG2` | 10 | FFT length 2^NFFT_LOG2 (4 ... 13 useful: the demo buffers hold 8192 samples) |
| `SCALE_SHIFT` | NFFT_LOG2-4 | total FFT scaling in bits (even). Raise it if the FFT output overflows, lower it for more dynamic range |
| `LIB` | `../pzsdr-p501/hdl/library` | ADI hdl library |
| `RUN` | none | `synth`, `impl` or `bit`: build right away. Or run `build.tcl` later (`-tclargs RUN=bit`) |
| `FFT` | 1 | `0` = leave the FFT chain out (with `DDS=0`: the base design only, the starting point of both tutorials) |
| `DDS` | 0 | `1` = add the DAC DDS ([DDS tutorial](tutorial/TUTORIAL_DDS.md)): it drives TX1 instead of the DAC DMA. `FFT=1 DDS=1` gives both |
| `JOBS`, `NAME` | 8, `p501_fft` | parallel jobs, project name (the overlay files are named after it). Defaults: `p501_fft`, `p501_dds`, `p501_fft_dds`, `p501_fft_tut` (neither) |

## How it works

* **Framing.** `adc_frame_gen` registers `{Q,I}` and a valid strobe from `axi_ad9361`. In 1R1T the valid is high every
  second `l_clk`, which the FFT core accepts (gaps in TVALID). It counts samples and raises TLAST every N, free-running.
* **FFT.** Pipelined streaming FFT, one sample per valid, natural-order output, bin *j* = frequency *j*·fs/N (negative
  frequencies in the upper half: `fftshift` it). The core wants one configuration word per frame; the length is fixed, so a
  constant is held on the config channel with TVALID high (forward transform + scaling schedule `SCALE_SHIFT`).
* **Power + frame gate.** `fft_power_gate` computes re^2+im^2 and passes a frame only if the DMA's `xfer_req` was high on
  its first bin. A DMA transfer therefore always starts on a frame boundary and gets whole frames; the FFT is never stalled.
  Program the DMA for `frames x N x 4` bytes and the next frames land in memory. The per-frame TLAST is *not* forwarded to
  the DMA: the ADI `axi_dmac` ends a transfer at the first TLAST, which would cut a multi-frame transfer after one frame.
* **Output.** 32-bit unsigned power per bin. Take `10*log10(avg + 1)` in Python.

## Verified

Built with Vivado 2024.1 (default options: N=1024, scale shift 6) and run on the board: the tone transmitted on bin 267 appears
on bin 267, 66 dB above the median floor, and the FPGA power matches NumPy's FFT of a raw ADC capture to 0.00 dB at the tone
(`notebook/P501_FFT_Example.ipynb` is saved with its outputs, `notebook/fft_result.png` is the figure). Post-route timing is met
(WNS +0.42 ns, WHS +0.01 ns); one minimum-pulse-width endpoint shows -0.002 ns, which comes from the reference base design.

## Using it from PYNQ

Copy `build/overlay/p501_fft.bit` and the fixed `p501_fft.hwh` to the board (same base name, same folder) and open
`notebook/P501_FFT_Example.ipynb`. In short:

```python
ol  = Overlay("/home/xilinx/jupyter_notebooks/p501_fft/p501_fft.bit")   # the FPGA now contains the FFT chain
# ... bring up the AD9361 exactly as in P501_AD9361_Test.ipynb (software side, unchanged) ...
dma = AxiDmac(ol.fft_dma)                       # same driver as for the ADC/DAC DMAs
buf = allocate(shape=(FRAMES, N), dtype=np.uint32)
dma.transfer_to_memory(buf.physical_address, buf.nbytes)     # FRAMES FFT frames of |X|^2
```

The AD9361 itself is still configured from software (SPI), so the notebook reuses the `ad9361_driver.py` flow.

## Things to know

* **`.hwh` fix.** PYNQ's metadata parser rejects two things Vivado emits for this design (orphan `sys_ps8` tie-off
  connections and the PS<->`gmii_to_rgmii` MDIO nets). `tools/fix_hwh.py` removes them; it reproduces the hand-fixed file used
  on the board (checked), and is idempotent.
* **Keep the whole base design.** Loading an overlay replaces the PL. The Ethernet port of this board runs through the PL
  (`gmii_to_rgmii`), so an overlay without it would take `eth0` down; USB networking is unaffected.
* **Clock `l_clk` = 2 x sample rate (1R1T).** Fine up to 61.44 MSPS (122.88 MHz). In 2R2T it is 4 x and the second channel
  would need a second chain (`adc_data_i1`, `adc_valid_i1`).
* **Limits of this starting point.** Rectangular window; fixed scaling; no averaging; the FFT is not back-pressured, so if the
  DMA stalls mid-frame (it should not at these rates) the frame is lost; the DMA interrupt is not wired to the PS.
  Natural next steps: a Hann window ROM before the FFT, K-frame averaging in BRAM, a CIC/FIR decimator for zoom FFT,
  run-time length and scaling via an AXI-Lite register block, two channels.
* **Warnings.** Vivado prints "connection ... overridden by the user" for a few pins of the new cells and one CRITICAL
  WARNING about `adf_spi_clk` having no FREQ_HZ; both come from interface inference / the reference design and are harmless.
